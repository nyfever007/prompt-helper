# 성능 기준선 (Sprint 2-C.4, TD-11)

- 목적: Sprint 2-D(시각 에셋·SVG) 이전의 제품 성능 기준선. 실제 제품 반응성과 테스트 도구 실행 비용을 구분합니다.
- 원본 데이터: [performance/](performance/)
  - `baseline-2c4-desktop.json`, `baseline-2c4-mobile-4x-cpu.json`: 브라우저 측정, 반복별 표본 포함
  - `bundle-2c4.json`: 번들 크기
  - `domain-2c4.json`: 도메인 함수 측정
- 다시 측정하는 방법:
  - `pnpm perf`: 제품 빌드 + 실제 Chromium. `pnpm verify`와 별개입니다.
  - `pnpm perf:bundle`: `pnpm build` 후 실행합니다.

- **데스크톱**: 모든 상호작용이 결과 반영까지 한 프레임 안(≤ 17ms), 화면 표시까지 2–3 프레임입니다.
- **모바일(CPU 4×)**: 결과 반영 중앙값이 13–28ms입니다. 처리 시간이 프레임 시간보다 짧아 그려진 시점은 데스크톱과 같은 프레임 단위입니다.
- 눈에 띄는 지연은 없습니다. 프리셋 적용의 최댓값(DOM 170ms, 그려짐 181ms)은 모바일 첫 회 1건입니다. 그려짐 기준 나머지 4회는 48–51ms입니다(첫 실행 시 코드 준비 비용으로 추정).
- 로딩: 모바일 앱 준비 약 0.39초, 복잡한 명세는 약 0.55초입니다. 대부분 JS 파싱·실행입니다(아래 번들 크기).
- 프리셋은 제품 카탈로그에 승인된 프리셋이 없어 테스트 전용 페이지(`/e2e-fixtures`)에서 쟀습니다.

## 5. 테스트 도구 비용과 제품 성능의 구분 — 500개 무작위 명세 속성 테스트

- 이 테스트는 명세 500개(카탈로그 2개 × 250개)를 만들어 각각 **두 번 컴파일**하고(결정성 확인), 결과를 깊은 비교합니다.
- 로컬 실측: 명세 생성 500개 36ms + 컴파일 1,000회 약 600ms + 비교·검증 ≈ **0.84–1.22초**. 기기 부하에 따라 변하며, 2-C.4 측정 중 0.94·1.22·0.94초였습니다.
- 제품 쪽 비용은 편집 1회당 컴파일 1회(복잡한 명세 0.82ms)입니다. 테스트 시간은 사용자 반응성과 직접 관련이 없습니다.

## 6. TD-11 판단 (Sprint 2-C.4)

- **부분 해결 유지**
  - 실제 제품 반응성에는 문제가 없습니다(§2–3).
  - CI는 제한 5초 안에서 안정적으로 통과합니다. 표의 CI 18회 실행에서 모두 통과했습니다(위 표).
  - 다만 느린 실행기에서는 “3초 이내” 목표를 넘습니다(3.0–3.5초).
- 남은 비용의 대부분은 테스트 설계상 필요한 컴파일 1,000회입니다. 영향이 큰 단일 병목은 없어 추가 최적화는 하지 않았습니다(ADR-055 최적화 유지). 검증 범위, 표본 수, 안전 검사, 제한 시간은 바꾸지 않았습니다.
- **Sprint 2-C.4 최종 승인**:
  - 부분 해결을 유지하며 추가 최적화는 하지 않습니다.
  - 이 문서의 측정 결과를 **Sprint 2-D 이후의 성능 비교 기준선**으로 씁니다.
  - `pnpm perf`와 `pnpm perf:bundle`은 `pnpm verify`에 넣지 않습니다(필요할 때 실행).
- **다시 검토할 조건**(하나라도 해당하면, 승인된 조건):
  - 느린 실행기에서 4.0초를 넘음
  - 제한 5초 초과로 CI가 실패함
  - Sprint 2-D 이후 속성 또는 규칙 규모가 현재(속성 348개, 규칙 114개) 대비 10% 넘게 늘어남
  - 실제 사용자 환경에서 성능 문제가 발견됨(참고 지표: §2의 결과 반영이 데스크톱 50ms, 모바일 CPU 4× 100ms를 꾸준히 넘음)

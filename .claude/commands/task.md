요청: $ARGUMENTS

코드를 고치기 전에 아래 세 가지를 먼저 정리해서 보여주고, 내가 확인하면 시작해.

1. **완료 기준 (행동 기준)**: "무엇이 되면 끝인가"를 사용자가 겪는 동작으로 3~5개.
   그럴듯하지만 틀린 구현과 구별되는 기준을 최소 1개 넣을 것.
   (예: "새 속성 추가 후에도 기존에 저장된 workspace가 경고 없이 그대로 열린다", "속성 A를 바꿔도 속성 B의 값은 그대로다")
2. **태스크 분해**: 태스크마다 어떤 테스트로 확인할지 — unit(`tests/unit`), component(`tests/component`), e2e(`e2e/`).
3. **영향 범위**: 바뀌는 모듈, 깨질 수 있는 기존 동작, 필요한 마이그레이션.

작업이 끝나면:
- 완료 기준마다 **실제 증거**를 보여줘: 해당 테스트 이름과 결과, 명령 출력 일부, UI라면 스크린샷 경로. "통과했습니다"만 쓰지 말 것.
- UI나 저장/복원 흐름이 바뀌었으면 `pnpm test:e2e`도 돌려 (Stop hook은 e2e를 돌리지 않음).
- 커밋은 내가 결과를 확인한 뒤에.
